# 同步辐射真空阀联锁 · 因果一致性服务

多个控制台可**离线提交**联锁操作，恢复联网后任意顺序重放；服务端按**因果前沿 +
依赖向量**原子裁决，保证**到达顺序不改变应有的因果状态**。值班员可建立包含
**2–5 个控制台**和若干阀门的轮次。页面经真实 HTTP 接口提交事件并实时呈现
阀门状态、因果前沿、等待项与放行/拒绝原因。

全部因果状态**持久化于提交日志**：进程退出或容器重建后，轮次的阀门、前沿、
等待项与既有裁决结论完整恢复，可继续操作。

## 语义模型

- **事件**：`event_id`（唯一标识）、`console`、`seq`（控制台本地序号）、
  `deps`（完整依赖向量：各控制台已消费序号）、`valve`、`expected_old`（期望旧状态）、
  `new_state`。
- **因果前沿**：每台控制台已消费的最大本地序号。仅当 `seq == 前沿+1` 且
  依赖向量全部被前沿覆盖时，事件才被**原子消费**（推进前沿 + 阀门转移 + 级联放行）。
- **消费即裁决**：期望旧状态匹配 → `applied`（放行并改阀）；不匹配 →
  `rejected_precondition`（拒绝但**照样推进因果位置**，后继永不阻塞）。
- **稳定裁决**：同批可放行项按 `event_id` 字典序依次消费——并发争用同一旧状态时
  较小标识成功，另一项稳定显示预条件拒绝。
- **幂等**：同一事件原样重投返回既有结论（等待中/已放行/已拒绝）；标识复用而
  载荷变化 → `409`。跳号、过期序号、未知控制台/阀门、未来依赖（依赖自身未来序号、
  未知控制台依赖、负依赖）→ `400`，且**不改任何阀门状态、不推进前沿**。

## 持久化与恢复

- **提交日志**：每次轮次创建与事件消费，都把该轮次的**完整因果状态**（阀门、
  前沿、全部事件记录、等待项、裁决顺序）作为一帧追加到
  `${DATA_DIR}/interlock.wal`。帧结构为
  `magic | 单调序号 | 载荷长度 | CRC32 | 载荷(JSON)`，写入即 `fsync`。
- **先落盘后应答**：创建轮次与消费事件的成功响应只在对应完整因果状态持久化
  之后返回；落盘失败时本次修改整体回滚并返回错误，重试不受污染。
- **恢复校验**：重启时逐帧校验 magic、序号链、CRC 与记录结构，**只接纳可证明
  完整的提交**；遇到截断或损坏尾部即回退（截断）到最后一致提交，既有轮次保持
  可继续操作。已消费事件按持久化结论直接恢复，**不重新裁决**。
- **数据目录**：容器内由 `DATA_DIR` 指定（镜像默认 `/data`，置空则退化为纯内存
  运行）；Compose 下宿主目录经 `APP_DATA_DIR` 配置（默认 `./data`，绑定挂载到
  容器 `/data`），容器重建后状态仍在。

## 运行

```bash
# 启动服务（宿主端口、数据目录均可配置）
docker compose up --build app
APP_HOST_PORT=9090 APP_DATA_DIR=/srv/interlock docker compose up --build app

# 健康入口与页面
curl http://localhost:8080/healthz        # {"status":"ok"}
open http://localhost:8080/               # 控制台页面（轮次列表点击可重新打开）
```

## 验收（verify）

```bash
docker compose up --build --exit-code-from verify --abort-on-container-exit
echo $?   # 0 = 验收通过
```

`verify` 容器依次执行并以退出码报告结果：

1. **构建检查** `go build ./...` 与静态检查 `go vet ./...`；
2. **代码测试** `go test ./...`（提交日志、引擎与 API 层单元测试）；
3. **因果场景 HTTP 冒烟**（`cmd/verify`）：
   - 依赖另一控制台的事件先到达 → 显示等待；补齐前驱 → 连续放行；
   - 两控制台争用同一旧状态 → 较小事件标识成功，另一项稳定预条件拒绝；
   - 竞争失败方的后继事件不被拒绝结果阻塞；
   - 同一事件重投返回既有结论；标识复用载荷变化/跳号/未知控制台/未来依赖
     均被明确拒绝且阀门状态不变；
   - **落盘时序**：轮次创建与事件提交的成功响应返回时，完整因果状态已在
     提交日志中；
   - **崩溃恢复**：向提交日志追加撕裂/损坏尾部后，经 `POST /admin/restart`
     触发进程重启——回退到最后一致状态，阀门、前沿、等待项与裁决原因完整
     重现，健康入口与原有轮次接口持续可用；
   - **重启后重放**：已放行/已预条件拒绝的标识重投返回原结论，复用标识改
     载荷仍 `409`；补交前驱后原等待链按事件标识规则连续放行；重启前后争用
     同一旧状态仍按稳定顺序裁决。

## HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/healthz` | 健康入口 |
| GET | `/` | 控制台页面 |
| POST | `/api/rounds` | 建立轮次：`{"id"?, "consoles":[2..5], "valves":{"GV1":"closed"}}` → `201` |
| GET | `/api/rounds` / `/api/rounds/{id}` | 轮次列表 / 状态（阀门、前沿、等待项、裁决记录） |
| POST | `/api/rounds/{id}/events` | 提交事件 → `200`(applied/rejected) / `202`(waiting) / `400` / `404` / `409` |
| POST | `/admin/restart` | 验收钩子：进程自我重启并从提交日志恢复（仅 `ENABLE_ADMIN_RESTART=1` 时注册） |

事件提交示例：

```json
{
  "event_id": "acc-b-001",
  "console": "beta",
  "seq": 1,
  "deps": {"alpha": 1, "beta": 0, "gamma": 0},
  "valve": "GV1",
  "expected_old": "closed",
  "new_state": "open"
}
```

响应携带裁决结论与最新轮次快照（`round`），页面据此渲染。

## 结构

```
cmd/app        服务入口（LISTEN_ADDR、DATA_DIR、ENABLE_ADMIN_RESTART）
cmd/verify     验收冒烟程序（APP_URL、DATA_DIR，退出码报告结果）
internal/causality  因果引擎：前沿、依赖向量、原子消费、级联、稳定裁决、幂等、快照持久化与恢复
internal/store      提交日志（WAL）：帧校验、fsync、损坏尾部回退
internal/server     HTTP API + 内嵌控制台页面
scripts/verify-entry.sh  verify 容器入口：构建检查 → 测试 → 冒烟
```
